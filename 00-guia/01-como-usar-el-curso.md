# Cómo usar este curso

**Audiencia:** programadores de software sin formación matemática especializada.  
**Última revisión:** 2026-08-25.

Cada lección usa cinco preguntas:

1. ¿Qué problema existía?
2. ¿Qué idea lo desbloqueó?
3. ¿Cómo funciona con una analogía de software?
4. ¿Qué puede salir mal?
5. ¿Qué invento hizo posible después?

## Convenciones visuales

> **Modelo mental**: una simplificación útil, no una definición formal.

> **No confundir**: dos ideas con nombres o efectos parecidos.

> **Frontera irregular**: el modelo puede resolver algo difícil y fallar en algo aparentemente trivial.

> **Veredicto**: clasificación de evidencia en casos llamativos.

## Escala de evidencia

| Nivel | Significa |
|---|---|
| A — confirmado | Fuente primaria, datos o informe de incidente verificable |
| B — sólido | Paper revisado o varias fuentes independientes coherentes |
| C — preliminar | Preprint, demo o resultado que aún necesita réplica |
| D — afirmación | Marketing, anécdota o interpretación no demostrada |
| F — falso/engañoso | La fuente original lo desmintió o el relato cambia el hecho esencial |

## Lo que “entender” significa aquí

Al terminar una lección deberías poder explicarla en una revisión de arquitectura, reconocer cuándo usarla y nombrar al menos un modo de fallo. No necesitas derivar las ecuaciones. Cuando una cifra es importante, se explica qué representa antes de mostrarla.

## Política de fuentes

- Se prefieren papers originales, documentación del producto, informes de seguridad y organismos públicos.
- Los blogs de fabricante sirven para fechas y descripciones, no como prueba neutral de superioridad.
- Las noticias se usan para contexto o para enlazar a una fuente primaria difícil de encontrar.
- “Open source” y “open weights” se distinguen: publicar pesos no implica publicar datos, receta ni licencia irrestricta.
- Toda cifra cambiante debe leerse junto a su fecha.
